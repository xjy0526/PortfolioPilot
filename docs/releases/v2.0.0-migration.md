# PortfolioPilot v2.0.0 Migration Guide

本文描述从旧 SQLite/个人 Dashboard 部署迁移到 v2.0.0 PostgreSQL 主线的安全顺序。命令必须先在
隔离环境演练。项目不执行真实交易，迁移也不会将旧持仓快照解释成完整交易历史。

## 1. 升级前准备

1. 记录当前应用 SHA、Alembic revision、数据库版本、对象存储版本和环境变量。
2. 备份 PostgreSQL/SQLite、对象存储和部署配置，并实际验证备份可读。
3. 停止会写入 ledger、行情、文档或 Workflow 的 Cron/Worker。
4. 确认 PostgreSQL 16 已启用 pgvector，应用使用 UTC。
5. 在 maintenance/read-only 窗口完成迁移，不在写流量下执行 schema 变更。

## 2. Alembic upgrade

先检查当前状态：

```bash
alembic current
alembic heads
```

再执行：

```bash
alembic upgrade head
alembic current
```

v2.0.0 当前 head 为 `20260821_0007`。不要修改任何已发布 migration revision；后续修复必须新增
revision 或显式 repair script。

## 3. Legacy snapshot generation

`20260821_0007` 创建 `legacy_snapshot_generations`，并按历史 import batch 回填 generation：

- 每个 portfolio/source 最多一个 `active` generation；
- 较旧 generation 保留审计并标记 `superseded`；
- `standard_csv`、`manual`、broker/API 等正式交易不被 supersede；
- 旧持仓 CSV 仍只表示 `opening_balance_only`。

迁移后至少核对：

1. 每个 legacy portfolio 是否只有一个 active generation；
2. active generation 是否关联预期 import batch；
3. 正式交易数量是否未改变；
4. 相同 snapshot 重放是否保持幂等。

## 4. Stale valuation scan 与 repair

`0007` 只迁移 generation metadata，不会自动重建已经存在的 valuation snapshot。当前 v2.0.0
候选树也不包含 `scripts/rebuild_stale_legacy_valuations.py`，因此不能声称升级后会自动修复旧累计估值。

安全处理步骤：

1. 找出存在 active `legacy_dashboard_csv` generation 的 portfolio；
2. 检查最新 valuation 的 `config_snapshot.data_source_context` 是否包含匹配的
   `legacy_snapshot_generation_id`；
3. 不匹配或缺少 lineage 时，将该 portfolio 标记为待重建，不继续把旧 valuation 当作有效结果；
4. 使用正式 API/Service 重建，而不是直接拼 SQL 修改 snapshot：

```bash
curl -X POST \
  "http://localhost:8000/api/portfolios/<portfolio_id>/rebuild?as_of=<ISO-8601-UTC>"
```

5. 重建后核对 generation ID、valuation `input_hash`、price/FX lineage 和持仓数量；
6. 逐 portfolio 记录成功/失败，不把部分成功报告成全量完成。

由于当前 LegacyPortfolioAdapter 对所有历史 mismatch 的 fail-closed 修复仍未进入 `main`，有旧 additive
legacy import 的部署应保持 read-only，直至扫描和重建完成。

## 5. SQLite 数据迁移

仅在确实存在旧库时执行：

```bash
python scripts/migrate_sqlite_to_postgres.py \
  --sqlite-path cache/portfoliopilot.db
```

治理数据使用独立脚本：

```bash
python scripts/migrate_governance_sqlite_to_postgres.py --help
python scripts/validate_governance_migration.py --help
python scripts/compare_sqlite_postgres_retrieval.py --help
```

先查看 `--help` 并使用隔离库。迁移完成前不删除 SQLite 文件；迁移完成后 SQLite 也不能重新成为事实源。

## 6. Demo 与 production 配置

仓库 fixture schema 见 `data/demo_fixture_manifest.json`，只允许用于 development/test/demo。

Development/synthetic smoke 可以使用：

```env
ENVIRONMENT=development
READ_ONLY_DEMO=true
EMBEDDING_PROVIDER=hashing
RAG_ALLOW_HASHING_FALLBACK=true
```

这些值不证明真实语义检索或模型效果。当前 release tree 没有 `make demo` 一键 governed seed，也没有
`DEMO_FIXTURE_MODE` production guard；不要引用未合并分支中的命令。

Production 必须使用真实依赖并关闭 hashing fallback：

```env
ENVIRONMENT=production
EMBEDDING_PROVIDER=sentence_transformers
RAG_ALLOW_HASHING_FALLBACK=false
```

## 7. S3-compatible storage

Development/test 可以使用 local storage。Production write mode 必须配置：

```env
OBJECT_STORAGE_BACKEND=s3
S3_ENDPOINT_URL=
S3_BUCKET=
S3_REGION=
S3_ACCESS_KEY_ID=
S3_SECRET_ACCESS_KEY=
S3_PREFIX=portfoliopilot
```

凭据只能通过 Secret Manager/部署平台注入。Web、Cron 与 Worker 必须使用同一个 bucket/prefix；它们的
本地文件系统不共享。`READ_ONLY_DEMO=true` 时可以不要求写对象存储，但所有 mutation 必须返回 403。

## 8. Preflight 与流量切换

迁移和 repair 完成后执行：

```bash
python -m app.core.preflight
```

Preflight 必须验证数据库、Alembic head、pgvector、对象存储、Embedding provider、认证和 read-only/
write-mode 约束。然后检查：

```bash
curl --fail http://localhost:8000/health/live
curl --fail http://localhost:8000/health/ready
```

推荐部署顺序：

```text
backup -> migration -> stale valuation scan -> rebuild -> preflight
       -> read-only smoke -> resume Worker/Cron -> enable traffic
```

Readiness 未通过时不得接入流量。

## 9. Rollback 边界

- 应用回滚：重新部署上一个已验证 image/SHA，不 force push 或改写 `main`。
- 数据库回滚：优先保留向后兼容 schema；只有在确认 v2 写入影响、拥有可恢复备份并完成隔离演练后，
  才考虑 `alembic downgrade -1`。
- 从 `0007` downgrade 会删除 generation metadata，可能使 legacy replace-snapshot 语义不可表达；
  不能在继续写入新 generation 后盲目 downgrade。
- 对象存储回滚必须与数据库 object version/checksum metadata 同步。
- 发生 ledger/valuation 异常时先切 read-only、停止 Worker/Cron并保留 run/trace，再调查或恢复备份。
- Rollback 后重新运行 migrations 状态检查、preflight、integration tests 和业务 smoke。

## 10. 发布后检查

1. 确认 `main` CI 六个 required Job 全部成功；
2. 确认 production image OCI version label 为 `2.0.0`；
3. 确认 OpenAPI `info.version` 为 `2.0.0`；
4. 确认没有真实持仓、内部文档或 Secret 进入仓库/日志；
5. 完成观察窗口后，再按单独指令创建 Tag 和 GitHub Release。
